AMD AI Engine Architecture

Hardware details of XDNA NPU tile arrays

Origins

AMD completed its acquisition of Xilinx in February 2022. The XDNA architecture descends directly from Xilinx's AI Engine technology, originally developed for the Versal Adaptive Compute Acceleration Platform (ACAP), first shipped in 2019. Versal combined traditional FPGA fabric with ARM processors and AI Engine coprocessors connected via a network-on-chip. AMD adapted and miniaturized this AI Engine tile array for integration as an NPU within consumer Ryzen processors.

AI Engine Lineage

  • AIE (Gen 1) — Original Versal ACAP AI Engine, 32 KB data memory per tile
  • AIE-ML / AIE2 — Versal AI Edge, doubled to 64 KB per tile, added int4 and bfloat16 support. Used in XDNA 1 (Phoenix/Hawk Point NPUs).
  • AIE-ML v2 / AIE2P — Used in XDNA 2 (Strix Point NPUs), 2x MACs per tile, new data types (MX6, MX9, Block FP16).

DMA and Data Movement

All data movement is explicit and programmer-controlled through DMA engines:

  • Compute tiles: 2 MM2S + 2 S2MM DMA channels each
  • Memory tiles: 6 MM2S + 6 S2MM DMA channels each
  • Shim tiles: DMA channels for host DDR access

DMAs are programmed via Buffer Descriptors (BDs) that specify transfer size, addresses, locks, and multi-dimensional address generation for on-the-fly tensor layout transformations. DMAs run independently and in parallel with computation.

ObjectFIFOs

The ObjectFIFO abstraction (from mlir-aie) provides a higher-level producer-consumer model for inter-tile communication. A producer calls acquire(N) to obtain N buffer slots, writes data, then calls release(N) to make them available to consumers. The underlying DMA engines handle the actual data transfers. Supports broadcast, join, distribute, and implicit copy patterns.

Tile Array Structure

Each column in the array contains (from bottom to top):

  • Row 0: Shim Tile — interface to host DDR via SoC fabric
  • Row 1: Memory Tile — L2 (512 KB)
  • Rows 2–5: Compute Tiles — L1 (64 KB each)

Tiles are connected by programmable circuit-switched and packet-switched stream interconnects. The array can be dynamically partitioned at column boundaries for spatial isolation of workloads.

VCK5000 / Versal ACAP

First-generation AI Engine platform — from Kimko & Cong, "When Systolic Arrays Meet AI Engines" (UCLA)

The Versal ACAP is the predecessor to the XDNA NPU found in Ryzen AI processors. It uses first-generation AIE1 cores (vs. AIE2/AIE2P in XDNA). Understanding it clarifies the lineage: many architectural concepts (tile arrays, stream switches, shared memory, DMA) carry forward, but the constraints differ significantly — AIE1 has smaller memories, no memory tiles, and a fundamentally different data movement model where compute kernels must manage forwarding.

Architecture Overview

The AMD Versal Adaptive Compute Acceleration Platform (ACAP) integrates three distinct compute domains on a single device:

  • AI Engine (AIE) Array — a grid of VLIW vector processors for high-throughput compute
  • Programmable Logic (PL) — traditional FPGA fabric for custom data movement and glue logic
  • Processing System (PS) — ARM cores for host control

These are connected by a programmable Network-on-Chip (NoC) that handles data movement between all three domains and off-chip DRAM.

AI Engine Array (AIE1)

The VC1902 device (used on VCK5000 and VCK190 boards) implements an 8 × 50 array of AIE1 cores operating at 1.25 GHz — that's 400 cores total.

VLIW Pipeline Slots (per cycle)

Each AIE1 core can issue up to 7 operations simultaneously:

  • 2 × move operations
  • 2 × vector loads
  • 1 × vector store
  • 1 × vector instruction (VMAC)
  • 1 × scalar instruction
This is the root cause of the "Systolic Tax": data forwarding between cores must be encoded as move/load/store instructions in the VLIW pipeline, competing with the vector instruction slot for execution resources. On traditional FPGAs, forwarding happens in dedicated routing fabric in parallel with compute — there is no such contention.

Critical limitation: Developers cannot explicitly initiate non-blocking AIE-to-AIE data transfers from within kernel code. The VLIW pipeline must wait for forwarding logic to complete before proceeding, serializing data movement with computation. This is the Forwarding-Compute Contention (FCC) component of the Systolic Tax.

Programmable Logic (PL)

The PL region serves as a high-throughput data mover between off-chip DRAM and the AIE array. Key design points:

  • DRAM bitwidth: 512-bit wide interface for maximum burst lengths
  • Target frequency: 312.5 MHz (to saturate PL-AIE interface at 1:4 ratio with 1.25 GHz AIE clock)
  • Minimum for DRAM saturation: 250 MHz
  • Uses a Load-Compute-Store paradigm with aggressive on-chip data reuse to bridge the bandwidth gap

The Systolic Tax

The fundamental performance penalty when mapping systolic arrays onto the AIE fabric. It has two components:

1. Forwarding-Compute Contention (FCC)

In a traditional systolic array on an FPGA, data forwarding between processing elements happens in dedicated routing fabric that operates in parallel with compute engines. On the AIE, forwarding must be encoded as explicit instructions in the compute kernel's VLIW pipeline. These forwarding instructions (acquire, forward, release) compete with VMAC operations for execution slots.

Measured cost: 8.2% of compute cycles consumed by input forwarding (averaged across 7.6–8.7% range).

2. Compute Cycle Interference (CCI)

Cycles where the processor stalls waiting for buffer synchronization — backpressure or latency from the AXI-Stream grid. This is induced by the forwarding pattern: more forwarding means more synchronization points, which means more potential stalls.

The 4-level tiling strategy breaks the GEMM into progressively smaller tiles, one for each physical boundary the data must cross. This page builds up the tiling one level at a time.

Level 1 — Off-Chip Tiling (DRAM → PL)

The outermost level partitions the full M×K×N problem into PL tiles of size Mp × Kp × Np. Each PL tile is a chunk of work small enough to fit in the FPGA's on-chip BRAM and URAM.

The Loop

for (tm1 = 0; tm1 < TM1; tm1++)        // TM1 = M / Mp
  for (tn1 = 0; tn1 < TN1; tn1++)      // TN1 = N / Np
    for (tk1 = 0; tk1 < TK1; tk1++)    // TK1 = K / Kp
      parallel_load(PL_tile_A, PL_tile_B);
      // ... inner levels process this tile ...
      parallel_store(PL_tile_C);

Each iteration loads one tile of A (size Mp × Kp) and one tile of B (size Kp × Np) from DDR4 into PL memory. After the inner levels finish computing, the result tile of C (size Mp × Np) is written back.

Why These Sizes?

The PL tile sizes are chosen to balance three competing constraints:

ConstraintWants tiles to be...Why
PL memory capacitySmallerA tile + B tile + C tile must fit in ~10 MB of BRAM + URAM (double-buffered)
DRAM latency hidingLargerCompute time on one tile must exceed load time of the next, to overlap via double-buffering
Data reuseLargerEach byte loaded from DRAM should be reused ~10× on-chip (due to the 10× bandwidth gap). Larger tiles = more reuse within the PL
Double buffering at this level: While the AIE array computes on PL tile i, the PL simultaneously loads PL tile i+1 from DRAM. The parallel_load and parallel_store in the pseudocode overlap with the inner compute loops. This only works if compute takes longer than communication — otherwise we're DRAM-bound. The MINLP optimizer (Section IV) solves for tile sizes that satisfy this condition.

Iteration Order

The loop nests M outside N outside K. This means we sweep across output tiles in row-major order, and for each output tile position, we accumulate all K chunks before moving on. The total number of DRAM loads is:

Total loads = TM1 × TN1 × TK1 = 4 × 6 × 8 = 192 tile-pair loads

How Long Does Each Load Take? (Equation 1)

The paper gives this formula for the number of PL cycles to load one PL tile's inputs from DRAM:

PL cycles = max(Mp × Kp, Kp × Np) / s × (wt / wd)

Each piece:

Putting it together step by step:

1. Bigger operand:  max(524,288, 360,448) = 524,288 elements
2. Split across channels:  524,288 / 2 = 262,144 elements per channel
3. Convert to PL cycles:  262,144 × (32/512) = 262,144 × 0.0625 = 16,384 PL cycles
4. Wall time:  16,384 / 312,500,000 Hz ≈ 52 µs per load
Intuition: the DRAM port is 512 bits wide, so it delivers 16 fp32 values per PL cycle. With 2 channels, that's 32 values per cycle. We need to move 524,288 values for the larger operand, so 524,288 / 32 = 16,384 cycles. The smaller operand (B) finishes earlier and simply waits.

Level 2 — PL Buffer Reuse (Temporal)

Once a PL tile is in on-chip memory, we don't send the entire thing to the AIE array at once. The SA (systolic array) is smaller than the PL tile, so we iterate over sub-tiles in time, reusing the data already loaded in PL memory.

The Loop

// Inside Level 1 (after parallel_load):
for (tm2 = 0; tm2 < TM2; tm2++)        // TM2 = Mp / Ms
  for (tn2 = 0; tn2 < TN2; tn2++)      // TN2 = Np / Ns
    for (tk2 = 0; tk2 < TK2; tk2++)    // TK2 = Kp / Ks
      // ... send SA-sized sub-tiles to the AIE array (Levels 3 & 4) ...

Each iteration selects one SA tile and sends it to the AIE array for processing.

What Is an "SA Tile"?

An SA tile is the block of the GEMM that the entire systolic array (all R × C cores running in parallel) computes in one invocation. It's not a physical structure — it's the logical unit of work per array activation:

  • SA tile of C (Ms × Ns) — the output block that all cores collectively produce. Each of the R×C cores computes one small Ma×Na piece of it.
  • SA tile of A (Ms × Ks) — the input slice that gets distributed across the array's rows (each row of cores shares the same rows of A).
  • SA tile of B (Ks × Ns) — the input slice that gets distributed across the array's columns (each column of cores shares the same columns of B).

SA Tile Dimensions

The SA tile size is determined by the array shape (R × C) and the per-core tile size (Ma × Ka × Na):

Ms = R × Ma = 8 × 16 = 128      (the full array height covers 128 rows of the output)
Ns = C × Na = 44 × 16 = 704      (the full array width covers 704 columns of the output)
Ks = Ka      = 64                 (each core processes 64 elements of K per invocation)

So the iteration counts are:

TM2 = Mp / Ms = 1024 / 128 = 8
TN2 = Np / Ns = 704  / 704 = 1
TK2 = Kp / Ks = 512  / 64  = 8

What Happens During One Level 2 Iteration

Each Level 2 iteration is one SA tile of A × one SA tile of B, producing a partial sum that accumulates into an SA tile of C. The PL orchestrates this loop — it reads sub-tiles from its BRAM/URAM buffers and streams them to the AIE array via PLIOs.

The PL's Role as Orchestrator

The Level 2 loop executes as a state machine in the PL. Here's what the PL does for each (tm2, tn2, tk2) iteration:

1. Read from PL buffers
PL reads A sub-tile and B sub-tile from BRAM/URAM at addresses determined by (tm2, tn2, tk2).
→
2. Stream to AIE via PLIOs
A slices multicast to rows, B slices multicast to columns. Double-buffered: this overlaps with step 3 of the previous iteration.
→
3. AIE cores compute
352 cores run Level 4 SIMD MAC in parallel. Each accumulates into its local C buffer. PL waits (or starts streaming next sub-tile).
→
4. After last tk2: flush
Results drain row-by-row back to PL. (Interleaved with next tm2's computation.)
Where the accumulation lives: The partial sum for each core's 16×16 output block stays in that core's 32 KB local memory (C_local in Algorithm 1) across all TK2=8 iterations. It never goes back to PL between tk2 steps. Only after tk2=7 finishes does the result get flushed down through the array rows and back to PL. This means the PL only needs to send A and B to the array — no C traffic during accumulation.

Double Buffering at the PL-AIE Boundary

Just like Level 1 double-buffers between DRAM and PL, Level 2 double-buffers between PL and the AIE array. While the AIE cores compute on SA tile i, the PL is already streaming SA tile i+1 to the AIE input buffers.

The PL-AIE communication time for one SA tile uses a similar formula to the DRAM load, but now through PLIOs instead of DRAM ports. The paper configures 128-bit PLIOs at 312.5 MHz, giving a 1:4 ratio with the 1.25 GHz AIE clock. The design is tuned so that AIE compute time ≥ PL-AIE communication time, ensuring the AIE array is never starved.

The Flushing Constraint: TK2 ≥ R

This is a critical constraint unique to the systolic mapping. After the SA finishes accumulating one output tile, the results must be flushed out of the array — drained row by row from top to bottom. A core at row r needs R−r−1 steps to pass its result down to the bottom edge.

Rather than stalling the whole array for R steps, the flush is interleaved with the next output tile's K-accumulation iterations. Each TK2 iteration does one flush step alongside the new computation. This only works if there are enough K iterations to complete the flush:

TK2 ≥ R
8   ≥ 8   ✓   (just barely satisfied)

If TK2 were smaller than R, the array would stall between output tiles waiting for the flush to complete.

Why this matters architecturally: The flushing constraint ties together the K tile size (Ks = Kp/TK2), the PL K tile size (Kp), and the array height (R). Making R larger (more rows) demands either a larger Kp or a smaller Ks. The MINLP optimizer in Section IV must balance this against memory capacity and compute efficiency.

Mapping Strategy: Independent Cores

Unlike the systolic approach in the Versal paper, here all NPU cores perform the same GEMM kernel independently on different data. There is no inter-core communication. The reduction across the K dimension is performed in time on each core, not spatially across cores.

The GEMM is parallelized in space across M and N dimensions only:

  • Each input A tile is broadcast across one row of the NPU array (all cores in that row get the same A rows)
  • Each input B tile is broadcast across one column of the NPU array (all cores in that column get the same B columns)
  • Output C tiles remain stationary in each core's L1 memory
  • The K reduction is done sequentially: each core loads successive K chunks, accumulates, and stores partial results in L1
Output stationary mapping: C tiles remain in L1 for the entire K reduction. Only A and B are streamed in. This is the opposite of the Versal design where outputs must be flushed through the systolic array rows. Here, there is no flush — each core writes its own result directly to L2 when done.

Conceptually similar to the Versal paper's 4-level hierarchy, but the physical boundaries are different:

Level 3: MemTile Staging (L2)

Level 2: Multi-Core Spatial Partitioning

Level 1 (innermost): Single-Core Kernel

The "Balanced Point" Optimization

The central insight: there is an inverse relationship between compute efficiency and DRAM pressure. The paper defines:

Compute time (Tcomp) — cycles for the GEMM kernel:
Tcomp = 2 · M · K · N / (eff · peak_TOPS)
Memory time (Tmem) — cycles for DRAM transfers:
Tmem = (Amem + Bmem + Cmem) / DRAM_BW
Optimal point:
Tcomp = Tmem   (the "balanced point")

If Tcomp > Tmem: compute-bound. Good — DRAM is not the bottleneck.
If Tcomp < Tmem: memory-bound. Bad — cores are idle waiting for data.

The optimal design is right at the crossover. The paper finds this point by:

  1. Profiling single-core GEMM efficiency (eff) and effective DRAM BW for each data type
  2. Starting with empirical values for ma, ka, na, and eff
  3. Iteratively decreasing ka (as a multiple of s) and solving exhaustively for each configuration
  4. Selecting the (ma, na) that maximizes MACs subject to L1 memory and DRAM BW constraints

L1 Memory Constraint

The kernel's tile sizes must fit in 64 KB. The paper uses a single C buffer (not double-buffered) to free L1 space for larger A and B tiles:

(2 · ma · ka · ty(A) + 2 · ka · na · ty(B)
 + ma · na · ty(C)) ≤ 64 KB

A and B are double-buffered (factor of 2) to overlap DMA with compute. C is single-buffered because it stays in L1 for the entire K reduction.

Data Movement: NPU ↔ DRAM

Buffer Descriptor (BD) Pipeline

Each ShimTile has access to 16 BDs. The paper's strategy:

  1. Submit 5 BDs per operand (A, B, C) = 15 BDs initially, utilizing 15 of 16 slots
  2. Each BD transfer begins immediately when its slot reaches the queue front
  3. B transfers start first (column-major needs more reshaping time)
  4. After each BD completes, the slot is reconfigured for the next transfer while others are in-flight
  5. Output C: command processor waits for task-completion tokens sequentially — but input BDs can overlap freely

BD Reconfiguration Overlap

A critical optimization: reconfiguring a BD (setting new addresses and dimensions for the next transfer) happens while previous transfers are still active. Without this, the paper measures a 27-28% performance degradation on both XDNA and XDNA2.

Roofline Behavior

Key findings from the GEMM sweeps across hundreds of matrix sizes (Figs. 7 & 8):

  • Small matrices (low arithmetic intensity): memory-bound. Performance scales linearly with AI.
  • Large matrices: performance saturates at the compute ceiling (peak TOPS).
  • B in row-major consistently outperforms B in column-major for XDNA (contiguous K-dimension access). For XDNA2, the gap is larger (19-25% higher) due to more complex NoC interactions.
  • XDNA2 has higher variability for B in row-major at lower AI values, attributed to the more complex DRAM-SoC fabric interaction.

Key Insights

1. Single Output Buffer Matters

By not double-buffering C, they free L1 for larger A and B tiles. This enables finding a better balanced kernel (more MACs per invocation). For XDNA2 with int8, the optimal balanced kernel is 112×28×96 with a single C buffer vs. 128×72×112 with double-buffered C — the double-buffered version has higher peak compute but worse overall GEMM performance because C tiles are transferred more often.

2. Data Layout in DRAM Matters Significantly

Storing B in row-major gives 4-9% higher performance on XDNA and 19-25% on XDNA2. The reason: contiguous DRAM access for both A and B when B is row-major. This is directly controlled by the kmt parameter (how many K tiles are loaded into MemTiles at once).

3. Reconfiguration Latency is Non-Trivial

Reconfiguring the NPU array for a different GEMM size takes 3.4 ms (XDNA) and 4.9 ms (XDNA2). For a 4K square GEMM that takes ~2 ms on XDNA2, this overhead is larger than the computation itself. However, only 2 parameters change between different GEMM sizes (tile count M and N), so reuse is possible.

4. Contiguous Elements in GEMM (C Buffer)

Accessing multiple contiguous output C elements across even columns (instead of odd) yields 2.4× (XDNA) and 3.6× better performance. This highlights the importance of the MemTile's neighboring memory sharing feature for output aggregation.

IR Walkthrough

How operations transform through each compilation stage, from Halide source to AIE machine code

Two parallel compilation paths run simultaneously: the compute path (shown below) generates the kernel that runs on each tile, while the dataflow path generates tile placement, ObjectFIFOs, and DMA sequences. Both merge into the final xclbin.

Example 1: Elementwise Add — C(i,j) = A(i,j) + B(i,j)

The simplest case: take two matrices A and B of the same size, and produce matrix C where each element is just A[i][j] + B[i][j]. There's no interaction between different positions — element (3,7) of C only depends on element (3,7) of A and B. This makes it the perfect starting example because there's no reduction (no summing across a dimension), and every element can be computed independently.

Stage 1: Halide Source

In Halide, you write the algorithm and the schedule separately. The algorithm says what to compute. The schedule says how to compute it efficiently on the target hardware.

The algorithm is just one line: C(i, j) = A(i, j) + B(i, j). Halide automatically understands that i and j range over all rows and columns. You never write explicit for-loops.

The schedule has three directives:

  • .tile(i, j, ..., 64, 64) — break the matrix into 64×64 blocks so each block fits in the AIE tile's 64 KB L1 memory (64×64 × 2 bytes = 8 KB per matrix, well within budget)
  • .parallel(io) — distribute the outer blocks across multiple AIE tiles for parallel execution
  • .vectorize(ji, 16) — process 16 elements at once using SIMD (single instruction, multiple data) within each tile
// Algorithm
Func A("A"), B("B"), C("C");
C(i, j) = A(i, j) + B(i, j);

// Schedule
C.tile(i, j, io, jo, ii, ji, 64, 64);
C.parallel(io);
C.vectorize(ji, 16);

Stage 2: Halide Lowered IR

Halide's compiler takes your clean one-line algorithm and "lowers" it — meaning it transforms it into something closer to what a machine actually executes. The Func abstraction disappears. What comes out is a nest of explicit for-loops with array reads and writes, similar to C code.

This is a lossy transformation: the original program said "C depends on A and B" through direct references. In the lowered IR, that relationship is only implicit — you'd have to analyze which buffers are read and written to figure it out. The compiler must do exactly this (DAG reconstruction) to set up ObjectFIFOs later.

allocate C_buf[int16, 64*64]
for io in 0..N/64:            // parallel (distributed to tiles)
  for jo in 0..M/64:
    for ii in 0..64:
      for ji in 0..64 step 16:   // vectorized
        C_buf[ii*64 + ji .. ji+15] =
          A_buf[...] + B_buf[...]

Stage 3: linalg.generic (MLIR)

Now we enter the MLIR world. MLIR (Multi-Level Intermediate Representation) is a compiler framework that represents programs at multiple levels of abstraction. linalg.generic is a powerful operation in MLIR's "linalg" dialect that can represent any element-wise or tensor operation — add, multiply, matmul, convolution — using a unified structure.

Instead of having separate code for "this is an add" vs. "this is a matmul," linalg.generic describes any operation through three pieces:

  • Indexing maps — how each tensor is accessed relative to the loop indices. For elementwise add, all maps are identity: (d0, d1) → (d0, d1), meaning A[i][j], B[i][j], and C[i][j] all use the same coordinates. For matmul, the maps would differ (A uses row and k, B uses k and column).
  • Iterator types — whether each dimension is "parallel" (can be computed independently) or "reduction" (must be accumulated). For elementwise add, both dimensions are parallel. For matmul, the k dimension is a reduction.
  • Body — the scalar operation applied per element. Here it's just arith.addi (integer add).

This is a key design insight: the compiler doesn't need a "GEMM builder" and a separate "elementwise builder." One representation handles everything.

#identity = affine_map<(d0, d1) -> (d0, d1)>

func.func @elementwise_add(
    %A: memref<64x64xi16>,
    %B: memref<64x64xi16>,
    %C: memref<64x64xi16>) {
  linalg.generic {
    indexing_maps = [#identity, #identity, #identity],
    iterator_types = ["parallel", "parallel"]
  } ins(%A, %B : memref<64x64xi16>)
    outs(%C : memref<64x64xi16>) {
  ^bb0(%a: i16, %b: i16, %c: i16):
    %sum = arith.addi %a, %b : i16
    linalg.yield %sum : i16
  }
  return
}

Stage 4: After Tiling (Transform Dialect)

The Halide .vectorize(ji, 16) directive gets translated into an MLIR Transform Dialect operation called tile_using_for. This breaks the linalg.generic that operated on the full 64×64 tile into many small invocations, each operating on a 1×16 slice.

Think of it like this: instead of saying "add these two 64×64 matrices," we're now saying "loop through the matrix 16 elements at a time, and add each 16-element strip." The memref.subview extracts the strip, and the linalg.generic inside the loop processes just that strip.

scf.for %i = 0 to 64 step 1 {
  scf.for %j = 0 to 64 step 16 {
    %a_slice = memref.subview %A[%i, %j][1, 16][1, 1]
    %b_slice = memref.subview %B[%i, %j][1, 16][1, 1]
    %c_slice = memref.subview %C[%i, %j][1, 16][1, 1]
    linalg.generic { ... }
      ins(%a_slice, %b_slice) outs(%c_slice)
  }
}

Stage 5: After Vectorization

Now the linalg.generic on the 1×16 slice gets replaced by actual vector instructions. Instead of a high-level "apply this operation to these slices," we get explicit loads of 16 elements into a vector register, a vector add instruction, and a vector store back to memory.

This is where the compiler makes a critical decision: it looks at the operation pattern. For elementwise add, there's no contraction (no reduction dimension, no multiply-accumulate). So it produces plain vector arithmetic (arith.addi on vectors). If this were a matmul, aie-opt would detect the contraction pattern and produce vector.contract instead — a fundamentally different operation.

scf.for %i = 0 to 64 step 1 {
  scf.for %j = 0 to 64 step 16 {
    %va = vector.load %A[%i, %j] : vector<16xi16>
    %vb = vector.load %B[%i, %j] : vector<16xi16>
    %vc = arith.addi %va, %vb : vector<16xi16>
    vector.store %vc, %C[%i, %j] : vector<16xi16>
  }
}

Stage 6: AIEVec Dialect

The previous stage used MLIR's generic vector dialect, which isn't specific to any hardware. Now convert-vector-to-aievec translates these into AIE-specific vector operations. The operations look almost identical, but they now use the aievec prefix, meaning they map directly to instructions the AIE hardware understands.

The vector width is target-dependent: 16 × i16 = 256 bits on AIE2, or 32 × i16 = 512 bits on AIE2P. The affine-super-vectorize pass earlier chose the right width based on the target device model.

scf.for %i = 0 to 64 step 1 {
  scf.for %j = 0 to 64 step 16 {
    %va = aievec.load %A[%i, %j] : vector<16xi16>
    %vb = aievec.load %B[%i, %j] : vector<16xi16>
    %vc = aievec.add %va, %vb : vector<16xi16>
    aievec.store %vc, %C[%i, %j] : vector<16xi16>
  }
}

Stage 7: LLVM IR → Native Code

The final step in the compute path. convert-aievec-to-llvm translates the AIEVec operations into LLVM IR — the same intermediate representation that C/C++ compilers (clang, gcc) use. LLVM IR is close to machine code but still portable across architectures.

Peano, AMD's LLVM-based compiler for AI Engine, takes this LLVM IR and compiles it into a native .o object file containing machine code that runs directly on the AIE tile's processor. This is the equivalent of what gcc -c does for CPU code.

Parallel: Dataflow (aie.mlir)

Everything above was the compute path — generating the kernel that runs on each tile. But a kernel alone isn't enough. The NPU also needs to know: which physical tiles should run this kernel? How does data flow between DDR memory and the tiles? How are input/output buffers connected?

The dataflow path answers these questions. It runs in parallel with the compute path and generates the spatial configuration — tile placement, ObjectFIFOs (inter-tile communication channels), and DMA instructions.

// Tile placement
%t0 = aie.tile(0, 2)
%t1 = aie.tile(0, 3)
// ... more tiles based on .parallel()

// ObjectFIFOs — two inputs, one output
aie.objectfifo @of_a(%shim0, {%t0, %t1}, 2)
    : !aie.objectfifo<memref<64x64xi16>>
aie.objectfifo @of_b(%shim0, {%t0, %t1}, 2)
    : !aie.objectfifo<memref<64x64xi16>>
aie.objectfifo @of_c({%t0, %t1}, %shim0, 2)
    : !aie.objectfifo<memref<64x64xi16>>

// Core logic
%core0 = aie.core(%t0) {
  %a = aie.objectfifo.acquire @of_a ...
  %b = aie.objectfifo.acquire @of_b ...
  %c = aie.objectfifo.acquire @of_c ...
  call @elementwise_add(%a, %b, %c)
  aie.objectfifo.release @of_a ...
  aie.objectfifo.release @of_b ...
  aie.objectfifo.release @of_c ...
  aie.end
}

aiex.npu.dma_memcpy_nd(...)

Example 2: GEMM — C(i,j) += A(i,k) * B(k,j)

Matrix multiply is fundamentally different from elementwise add. To compute a single element C[i][j], you need an entire row of A (row i) and an entire column of B (column j), and you multiply them element-by-element and sum the results. This "sum over k" is a reduction — multiple input values collapse into one output value. This changes everything: the indexing maps are no longer identity, we need an accumulator to hold partial sums, and data must be streamed in chunks because the full row/column may not fit in L1.

Stage 1: Halide Source

The algorithm is three lines. RDom r(0, K) declares a "reduction domain" — a loop variable that will be summed over (the k in the formula). C(i,j) = 0.0f initializes the output to zero. C(i,j) += ... says "for each (i,j), accumulate over all values of r." The casts convert bf16 inputs to f32 for the accumulation to avoid precision loss.

The schedule has four directives:

  • .tile(i, j, ..., 64, 32) — compute 64×32 blocks of the output matrix C at a time
  • .split(r.x, ro, ri, 64) — break the dot product (length K) into chunks of 64, because loading the entire row/column at once would overflow L1
  • .reorder(...) — control loop nesting order to maximize data reuse in L1
  • .vectorize(ji).vectorize(ii) — use SIMD for both inner dimensions
// Algorithm: C = A * B    (bf16 -> f32)
RDom r(0, K);
C(i, j) = 0.0f;
C(i, j) += cast<float>(A(i, r)) * cast<float>(B(r, j));

// Schedule
C.tile(i, j, io, jo, ii, ji, 64, 32);    // spatial tiles: 64x32 output block
C.split(r.x, ro, ri, 64);                 // reduction tiles: chunks of 64
C.reorder(ri, ii, ji, ro, io, jo);         // loop order
C.vectorize(ji).vectorize(ii);             // SIMD

Stage 2: Halide Lowered IR

After lowering, the algorithm becomes six nested loops. Understanding the loop structure is critical:

  • io, jo (outermost) — iterate over 64×32 blocks of the output matrix. Each iteration selects which block of C we're computing. On the NPU, these correspond to which tile processes which block.
  • Accumulator init — zero out the 64×32 accumulator buffer before starting the dot product.
  • ro (middle) — iterates over chunks of the K dimension. Each iteration loads a new 64×64 slice of A and a new 64×32 slice of B from L2 into L1 via DMA. This is the "streaming" loop — it drives the ObjectFIFO acquire/release pattern.
  • ri, ii, ji (innermost) — the actual multiply-accumulate computation within one chunk. These loops are vectorized and map to aie::mmul hardware instructions.
  • Write back — after all K chunks are processed, the final accumulated result is written from L1 back to L2/DDR.
for io in 0..M/64:              // which 64-row block of C
  for jo in 0..N/32:            // which 32-col block of C
    // initialize accumulator
    for ii in 0..64:
      for ji in 0..32:
        C_acc[ii][ji] = 0.0f

    for ro in 0..K/64:          // stream K-dimension in chunks of 64
      for ri in 0..64:          // reduction within chunk
        for ii in 0..64:        // rows within tile (vectorized)
          for ji in 0..32:      // cols within tile (vectorized)
            C_acc[ii][ji] += float(A[io*64+ii][ro*64+ri])
                           * float(B[ro*64+ri][jo*32+ji])

    // write back accumulator
    for ii in 0..64:
      for ji in 0..32:
        C[io*64+ii][jo*32+ji] = C_acc[ii][ji]

Working set per inner block: A tile (64×64 × 2B = 8 KB) + B tile (64×32 × 2B = 4 KB) + C accumulator (64×32 × 4B = 8 KB) = 20 KB. Fits in 64 KB L1.

Stage 3: linalg.generic (MLIR)

This is where the structural difference between elementwise and matmul becomes mathematically precise. Compare side-by-side:

Elementwise add: C[i][j] = A[i][j] + B[i][j]. All three tensors use the same indices (i,j). Two dimensions, both parallel.

Matmul: C[i][j] = sum_k( A[i][k] * B[k][j] ). A uses (i,k), B uses (k,j), C uses (i,j). Three dimensions, where k is a reduction — it doesn't appear in the output.

The linalg.generic captures this difference through:

  • Three loop dimensions (d0=i, d1=j, d2=k) instead of two
  • Non-identity indexing maps: A → (d0, d2) means A is indexed by (i, k); B → (d2, d1) means B is indexed by (k, j); C → (d0, d1) means C is indexed by (i, j). The shared dimension d2 (k) appearing in both A and B but not C tells the compiler "this is a contraction along k."
  • Iterator types include "reduction" for d2 — this explicitly marks the k dimension as one that must be accumulated, not parallelized.
  • Body has cast + multiply + add (the fused multiply-accumulate), not just add. The accumulator input %c carries the running sum.
#map_a = affine_map<(d0, d1, d2) -> (d0, d2)>   // A(i, k)
#map_b = affine_map<(d0, d1, d2) -> (d2, d1)>   // B(k, j)
#map_c = affine_map<(d0, d1, d2) -> (d0, d1)>   // C(i, j)

func.func @matmul(
    %A: memref<64x64xbf16>,
    %B: memref<64x32xbf16>,
    %C: memref<64x32xf32>) {
  linalg.generic {
    indexing_maps = [#map_a, #map_b, #map_c],
    iterator_types = ["parallel", "parallel", "reduction"]
  } ins(%A, %B : memref<64x64xbf16>, memref<64x32xbf16>)
    outs(%C : memref<64x32xf32>) {
  ^bb0(%a: bf16, %b: bf16, %c: f32):
    %a_f32 = arith.extf %a : bf16 to f32
    %b_f32 = arith.extf %b : bf16 to f32
    %prod = arith.mulf %a_f32, %b_f32 : f32
    %sum  = arith.addf %c, %prod : f32
    linalg.yield %sum : f32
  }
  return
}
The same linalg.generic container is used for both elementwise and matmul. The operation type is determined entirely by the indexing maps and iterator types, not by separate code paths. Softmax (reduction + elementwise), conv2d (stencil access in indexing maps), and attention all use this same representation.

Stage 4: After Tiling (Transform Dialect)

The 64×64 A tile and 64×32 B tile are still too large for a single hardware mmul instruction. The hardware can only multiply small blocks at a time — for bf16 on AIE2, the micro-kernel shape is mmul<4,8,4>, meaning it multiplies a 4×4 block of A by a 4×8 block of B in one instruction.

So tiling adds three more loops that decompose the 64×64×32 tile into many 4×4 × 4×8 micro-operations. The linalg.generic now operates on micro-kernel-sized slices inside the loops. The step sizes (4, 8, 4) come from the micro-kernel catalog in the device model.

scf.for %i = 0 to 64 step 4 {        // tile rows by micro-kernel r
  scf.for %j = 0 to 32 step 8 {      // tile cols by micro-kernel s
    scf.for %k = 0 to 64 step 4 {    // tile reduction by micro-kernel t
      %a_tile = memref.subview %A[%i, %k][4, 4][1, 1]
      %b_tile = memref.subview %B[%k, %j][4, 8][1, 1]
      %c_tile = memref.subview %C[%i, %j][4, 8][1, 1]
      linalg.generic { ... }
        ins(%a_tile, %b_tile) outs(%c_tile)
    }
  }
}

The inner tile sizes (4×4 for A, 4×8 for B) are determined by the micro-kernel shape mmul<4,8,4> for bf16 on AIE2.

Stage 5: After Vectorization

This is the critical divergence point between elementwise and matmul. The aie-opt pass examines the linalg.generic body and indexing maps. It sees a multiply followed by an add, with a reduction iterator type — the signature of a tensor contraction. So instead of producing plain vector arithmetic (like arith.addi for elementwise), it produces vector.contract.

vector.contract is MLIR's way of saying "take two small matrices, multiply them, and accumulate the result into an output matrix" — all in one operation. It preserves the indexing maps and reduction semantics from linalg.generic, but now operates on vector registers. Notice how the accumulator %vc is loaded outside the k-loop and stored after the k-loop — it accumulates across all K chunks in a register, avoiding repeated memory writes.

scf.for %i = 0 to 64 step 4 {
  scf.for %j = 0 to 32 step 8 {
    // load accumulator
    %vc = vector.load %C[%i, %j] : vector<4x8xf32>
    scf.for %k = 0 to 64 step 4 {
      %va = vector.load %A[%i, %k] : vector<4x4xbf16>
      %vb = vector.load %B[%k, %j] : vector<4x8xbf16>
      %vc_new = vector.contract {
        indexing_maps = [...],
        iterator_types = ["parallel", "parallel", "reduction"]
      } %va, %vb, %vc : vector<4x4xbf16>, vector<4x8xbf16> into vector<4x8xf32>
    }
    // store accumulator
    vector.store %vc, %C[%i, %j] : vector<4x8xf32>
  }
}

vector.contract is MLIR's representation of a tensor contraction at the vector level. It preserves the indexing maps and reduction semantics from linalg.generic.

Stage 6: AIEVec Dialect

vector.contract is still a generic MLIR operation. Now it gets lowered to aievec.matmul, which is a 1:1 mapping to the AIE hardware's aie::mmul<4,8,4> intrinsic. This is the actual hardware multiply-accumulate instruction that processes a 4×4 block of A and a 4×8 block of B in a single cycle.

On AIE2P (NPU2), the same code would use aie::mmul<4,8,8> instead — wider accumulators allow processing a 4×8 block of B instead of 4×4. The compiler selects the right intrinsic shape from the device model automatically.

scf.for %i = 0 to 64 step 4 {
  scf.for %j = 0 to 32 step 8 {
    %acc = aievec.load %C[%i, %j] : vector<4x8xf32>
    scf.for %k = 0 to 64 step 4 {
      %va = aievec.load %A[%i, %k] : vector<4x4xbf16>
      %vb = aievec.load %B[%k, %j] : vector<4x8xbf16>
      %acc = aievec.matmul %va, %vb, %acc
          : vector<4x4xbf16>, vector<4x8xbf16> into vector<4x8xf32>
    }
    aievec.store %acc, %C[%i, %j] : vector<4x8xf32>
  }
}

The accumulator (vector<4x8xf32>) lives in the 512-bit accumulator register on AIE2 (2048-bit on AIE2P). The aievec.matmul fuses the multiply and accumulate into a single hardware operation.

Stage 7: LLVM IR → Native Code

Same as elementwise: convert-aievec-to-llvm produces LLVM IR, and Peano compiles it to native machine code.

But GEMM has an extra optimization: the linalg path "peels" the first iteration of the K-loop out of the main loop. Why? Because the first iteration initializes the accumulator, while subsequent iterations just accumulate. Peano's software pipeliner can then overlap DMA transfers for the next K-chunk with computation of the current chunk — but only if the loop body is uniform (every iteration does the same thing). Peeling the first iteration makes the remaining loop body uniform.

Parallel: Dataflow (aie.mlir)

The GEMM dataflow is significantly more complex than elementwise. Three key differences:

  • Double-buffering (depth = 2): For elementwise, each tile processes one block and is done. For GEMM, each tile processes K/64 input block pairs for every output block. The reduction loop streams data continuously. With depth 2, the DMA can fill buffer slot 1 while the compute core processes buffer slot 0, then they swap — hiding the DMA latency behind computation.
  • Broadcast patterns: In a 4×4 tile grid computing GEMM, all tiles in the same row need the same row-block of A, and all tiles in the same column need the same column-block of B. So A is broadcast within each device row, and B is broadcast within each device column. This is the 2D outer-product decomposition from Figure 3 in the paper.
  • 36 ObjectFIFOs for 16-core GEMM: each tile needs an A input, B input, and C output channel, plus the shim-to-memory-tile and memory-tile-to-compute-tile connections at each level of the memory hierarchy.
// Tile placement: 4x4 grid for 16-core GEMM
%t00 = aie.tile(0, 2)    %t01 = aie.tile(0, 3)
%t10 = aie.tile(1, 2)    %t11 = aie.tile(1, 3)
// ... 12 more tiles

// ObjectFIFOs with broadcast
// A rows: shim -> all tiles in same row (broadcast within row)
aie.objectfifo @of_a_row0(%shim0, {%t00, %t10, %t20, %t30}, 2)
    : !aie.objectfifo<memref<64x64xbf16>>

// B cols: shim -> all tiles in same column (broadcast within column)
aie.objectfifo @of_b_col0(%shim0, {%t00, %t01, %t02, %t03}, 2)
    : !aie.objectfifo<memref<64x32xbf16>>

// Core logic: acquire, compute reduction loop, release
%core0 = aie.core(%t00) {
  %c_buf = aie.objectfifo.acquire @of_c ...
  // initialize accumulator to zero
  scf.for %ro = 0 to K/64 {
    %a_buf = aie.objectfifo.acquire @of_a_row0 ...
    %b_buf = aie.objectfifo.acquire @of_b_col0 ...
    call @matmul(%a_buf, %b_buf, %c_buf)
    aie.objectfifo.release @of_a_row0 ...
    aie.objectfifo.release @of_b_col0 ...
  }
  aie.objectfifo.release @of_c ...
  aie.end
}

// Runtime: host-to-device DMA with strided access
aiex.npu.dma_memcpy_nd(0, 0, %arg0[...]) {
    metadata = @of_a_row0, id = 0 } : memref<512x512xbf16>

§1–2 — Introduction, Background & Related Work

Hardware recap (vocabulary)

  • AIE = 2D array of high-frequency VLIW vector processors, 20–400 cores depending on device family.
  • Cores communicate via DMA over AXI stream networks + switches.
  • Three-level scratchpad hierarchy: L1 = per-core local memory; L2 = on-chip buffers on the PL (FPGA) or memory tiles shared across cores; L3 = off-chip DRAM.
The L2 duality (FPGA buffers vs. shared memory tiles) is the AIE-only-vs-AIE+FPGA split that motivates the entire paper's unified-IR argument.

The conceptual spine: five levels of parallelism

Everything in the §4 programming model maps back to these:

#LevelMechanism
1Task-levelmap each task to a specific AIE core group
2Tile-levelpartition a task's loop nest into tiles, run across multiple cores
3Loop-levelpipeline instructions within a loop
4Data-levelSIMD vector engines
5Instruction-levelVLIW instruction bundling

§4.1–4.3 handle levels 1–2 (across cores); §4.4 "Intra-Tile Parallelism" handles levels 3–5 (within a core) via declarative scheduling.

The four challenges (motivation)

  1. Limited support for multi-layer applications. Prior work accelerates single kernels (MM, stencil). Scaling to multi-layer apps needs workload partitioning across heterogeneous components + inter-layer communication control.
  2. Fragmented abstraction for multi-level parallelism (the central gap). Riallto / MLIR-AIE use a dataflow model that captures task-level parallelism cleanly but cannot express tile-level parallelism inside a task. Splitting a task across cores means manually breaking loop tiles into separate kernels, placing each, and hand-coordinating data movement. Intra-core parallelism means inserting C++ pragmas + calling C++ vector intrinsics → abstraction fragmented across levels.
  3. Limited automation / optimization. Riallto / MLIR-AIE rely on the user for dataflow, inter-tile movement, vectorization. MLIR-AIR automates but ignores FPGA-side dataflow / datatypes / buffer reuse. AMD Vitis splits AIE (ADF graphs) from PL (HLS/RTL) with a separate connection config file → no holistic optimization.
  4. Portability. Ryzen-AI NPU (consumer; fewer AIE-ML cores + mem-tiles as L2) vs. Versal ACAP (datacenter; more cores + integrated FPGA). Works target one or the other; porting is labor-intensive.

ARIES's three contributions (the answers)

  1. Programming model — define tasks at tile granularity, scale task tiles across cores without restructuring code; plus declarative scheduling primitives to tune a single tile on a single core.
  2. First unified MLIR IR spanning three layers: AIEVec dialect (single AIE core) + proposed ADF dialect (AIE array / graph) + builtin dialects (memref / scf / affine, for PL). Enables global + local optimization; reaches up to 87% AIE efficiency at hundreds of cores.
  3. Portability — one source → both Versal ACAP and Ryzen NPU via lightweight codegen backends.

§4 — ARIES Programming Model

4.1 Motivating Example: MLP with Tiled GEMM

Basic GEMM C[i,j] = Σk A[i,k]·B[k,j] is a 3-level loop nest. Mapping it directly to AIE is bad for two reasons:

  • Parallelism: I, J, K are far larger than the AIE array → you can't just unroll across cores, and wrong unroll factors actively hurt.
  • Memory: inputs/outputs don't fit in L1 → they sit in slow L3 → no locality, no on-chip reuse.

The fix is loop tiling — but the paper deliberately shows the imperative version (Figure 4) to expose its cost. You hand-write a 4-deep tiled nest where each level maps to a hardware tier:

T = int(16)                                    # ① datatype: 16-bit integer

def gemm_tiled(A: T[I,K], B: T[K,J], C: T[I,J]):
  # ══ LEVEL 0 ══ TEMPORAL · which L2 tile ════════════════  [step = TI_0]
  for i0 in range(0, I,    TI_0):              #  I / TI_0  outer steps
    for j0 in range(0, J,    TJ_0):
      for k0 in range(0, K,    TK_0):          #  ← k is the REDUCTION axis
        DMA_LOAD_L3_TO_L2(...)                 #  DRAM(L3) → on-chip L2 buffer
        # ══ LEVEL 1 ══ TEMPORAL · which L1 tile ══════════  [step = TI_1]
        for i1 in range(0, TI_0, TI_1):        #  TI_0 / TI_1 steps
          for j1 in range(0, TJ_0, TJ_1):
            for k1 in range(0, TK_0, TK_1):
              DMA_LOAD_L2_TO_L1(...)           #  L2 → core-local L1
              # ══ LEVEL 2 ══ SPATIAL · which CORE ════════  [step = TI_2]
              for i2 in range(0, TI_1, TI_2):  #  TI_1 / TI_2 sub-tiles
                for j2 in range(0, TJ_1, TJ_2):#    → distributed across AIE cores
                  for k2 in range(0, TK_1, TK_2):
                    LOAD_L1_TO_VECTOR_REGS(...) #  L1 → vector registers
                    # ══ LEVEL 3 ══ SIMD · inside ONE core ══  [extent = TI_2]
                    for i3 in range(0, TI_2):
                      for j3 in range(0, TJ_2):
                        for k3 in range(0, TK_2):
                          MAC(A_vec, B_vec, C_vec)  # multiply-accumulate
                    store(C_vec, C_L1, ...)    #  vector regs → L1
              DMA_STORE_L1_TO_L2(...)          #  L1 → L2 (finished result tile)

Mental model: a 4-level "tile telescope"

Each matrix dimension (I, J, K) is tiled four times, once per hardware boundary. The reading trick: each level's step is the total extent of the level below it — that's why i0 steps by TI_0, i1 runs 0…TI_0 by TI_1, i2 runs 0…TI_1 by TI_2, i3 runs 0…TI_2. They nest like Russian dolls: TI_0 ⊇ TI_1 ⊇ TI_2 ⊇ (1 element).

LevelIndicesLoop bound / step#iters (I-dim)Hardware roleMemory action
0i0,j0,k0range(0, I, TI_0)I / TI_0temporal — outer scheduleDMA_LOAD_L3_TO_L2 (DRAM→L2)
1i1,j1,k1range(0, TI_0, TI_1)TI_0 / TI_1temporal — L1 stagingDMA_LOAD_L2_TO_L1 (L2→L1)
2i2,j2,k2range(0, TI_1, TI_2)TI_1 / TI_2spatial — pick AIE coreLOAD_L1_TO_VECTOR_REGS (L1→regs)
3i3,j3,k3range(0, TI_2)TI_2SIMD — lanes in one coreMAC then store (regs→L1)

One AIE core's job per visit = compute a TI_2 × TJ_2 × TK_2 block of MACs; the level-2 loops enumerate which core / sub-tile, while level-0/1 are the temporal sweep streaming data inward through L2 then L1.

"Where what goes" — the two things you hand-place

(a) Memory ops are pinned to the loop level whose tile they stage — a matched ladder, load on the way in / store on the way out:

L0 enter →  DMA L3→L2          (stage the big L2 tile)
  L1 enter →  DMA L2→L1        (stage the L1 tile)
    L2 enter →  L1→regs        (feed one core)
      L3 →  MAC × (TI_2·TJ_2·TK_2)
    L2 exit  →  regs→L1  (store)
  L1 exit  →  DMA L1→L2        (evacuate the result tile)

Every DMA_* placement is a manual decision — choose the level too high and you re-stage data you already have; too low and you thrash the DMA. (Pain-point #1, made concrete.)

(b) The K-axis is a reduction, which silently constrains everything. k0,k1,k2,k3 tile the contraction dimension, so for a fixed output (i,j) the partial products from all K-tiles must accumulate into the same C tile:

  • C_vec accumulates across k3 (innermost);
  • across k2 / k1 / k0 the partial sums keep accumulating in C_L1 — note store(C_vec, C_L1) is read-modify-write;
  • consequence: a C tile must not be evacuated to L2/L3 until its entire K-sweep finishes. Loop ordering is load-bearing — get it wrong and you write out partial garbage.
The reuse of B across i, of A across j, and the accumulation of C across k are all invisible in the code — nothing names them. Recovering them for optimization is exactly what needs polyhedral analysis. (Pain-point #2.)
This imperative approach "works" but creates two new problems — the whole motivation for §4.2:
  1. Massive code restructuring — build the deep nest, decide which loop level maps to cores, and hand-place every DMA between memory tiers.
  2. Data reuse is implicit — recovering it needs heavy compiler analysis (polyhedral) to spot reusable data and avoid redundant off-chip traffic.

4.2 Tile-Based Task Abstraction

ARIES's move: you write the kernel for a single tile, as if it were the whole problem. Tiling on (i,j,k) turns the task into a 3D grid of tiles; the task is done when every grid cell is processed (Figure 5):

@aries.task_tile
def gemm(A: T[I,K], B: T[K,J], C: T[I,J]):
    i, j, k    = aries.tile_ranks()    # which tile in the grid
    TI, TJ, TK = aries.tile_sizes()    # tile sizes (set outside the fn)
    ti = arange(i*TI, (i+1)*TI)        # this tile's index ranges
    tj = arange(j*TJ, (j+1)*TJ)
    tk = arange(k*TK, (k+1)*TK)
    A_L1: T[TI,TK] = A[ti,tk]          # load slice to L1
    B_L1: T[TK,TJ] = B[tk,tj]
    C_L1: T[TI,TJ] = C[ti,tj]
    for i in range(TI):                # plain inner loops, no DMA juggling
      for j in range(TJ):
        for k in range(TK):
          C_L1[i,j] += A_L1[i,k] * B_L1[k,j]
    C[ti,tj] = C_L1                    # store partial sum

What vanished vs. Figure 4: the 4-deep nest, the explicit DMA_LOAD_L3_TO_L2/L2_TO_L1 calls, and the core-mapping loop levels. Three concepts make this work:

  1. Grid semantics — tile_ranks() / tile_sizes() index a tile in the grid; the CUDA / Triton idiom (write one tile, the grid is implicit). Concise without losing expressiveness. Special case: a 1-tile grid ⇒ tile size = full problem ⇒ no tile-level parallelism.
  2. Tile-based memory abstraction — memories are described per tile: external params → L2/L3, locals (A_L1, …) → L1. Accesses become hyper-rectangles in memory space, so the compiler finds reuse by checking overlap between tiles' regions. Example: all tiles along the i dimension share the same B tile → cache it in L2 and broadcast. This is the payoff — reuse goes from implicit (needs polyhedral analysis) to explicitly analyzable geometry.
  3. Decoupled scheduling (borrowed from Allo) — the algorithm in the task function never changes; mapping/execution is set separately via primitives (Table 1).
Primitive (Table 1)EffectParallelism level
.to(tiles, cores)map tile(s) → designated AIE core(s)① task + ② tile
.pipeline(axis, factor)instruction pipelining on a loop axis③ loop
.vectorize(axis, factor)vectorize loop axes④ data (SIMD)
Core insight: ARIES decouples what each tile computes (the @task_tile function — written once, for one tile) from how tiles map to hardware (the scheduling primitives). That decoupling is what makes "scale across cores without restructuring code" literally true — the direct answer to Challenge 2 from §1. Level ⑤ (VLIW/ILP) isn't a primitive; it's left to the backend.

4.3 Task- and Tile-Level Parallelism (the .to() primitive)

Setup: a two-layer MLP on a Ryzen-AI NPU with a 4×5 AIE array. Tile sizes are set via the subscript operator; each task returns a handle; a Schedule object applies customization to task0 and task1. Then .to() maps tiles → cores — two ways (Figure 6):

from aries.targets import NPU
sch = aries.Schedule([task0, task1])

# Case 1: Automatic — hand a whole tile-set to a core region, ARIES distributes
sch.to(task0.tiles(), NPU[:4, :2])          # rows 0-3, cols 0-1  → 8 cores

# Case 2: Explicit — place each tile yourself
for (i, j, k), tile in enumerate(task1.tiles()):
    sch.to(tile, NPU[i%4, 2+j%2])           # → region NPU[:4, 2:4]
  • Case 1 (automatic): give all of task0's tiles to a rectangular core region and let ARIES spread them.
  • Case 2 (explicit): compute each tile's destination by hand.
  • Note task0 → cols 0-1 and task1 → cols 2-3: the two MLP layers run on separate core groups in parallel (task-level parallelism).
The subtle, important bit: the explicit map NPU[i%4, 2+j%2] uses only i and j, not k. So every tile sharing an (i,j) but differing in k lands on the same core → the K-reduction partial sums stay local → the GEMM runs in output-stationary dataflow. This is the payoff of the Figure 4 K-reduction observation: the scheduling choice (which axes you map) selects the dataflow strategy. Map k to cores instead → a reduction-spread dataflow needing cross-core accumulation.

Cross-tile communication is derived, not written. Once placement is set, ARIES picks the data-movement mechanism automatically, in three tiers:

SituationMechanism
Communicating tiles on adjacent coresfast DMA — one core directly reads the other's L1
Tiles on non-adjacent coresAXIS streaming through hops of on-chip switches
A core's inputs exceed its stream-channel limitgather in L2/L3 first, then forward to the destination

The user controls placement; the communication falls out of it — the §4.2 "no restructuring" promise extended to inter-core data movement.

4.4 Intra-Tile Parallelism (.pipeline / .vectorize)

Now optimize within one core (Figure 7):

axes = task0.get_loops()
# Loop-level parallelism (③): instruction pipelining
sch.pipeline(axes[0], range=(1, 64))
# Data-level parallelism (④): SIMD vectorization
sch.vectorize(axes, factors=[4, 8, 4])
  • .pipeline() → inserts a directive into the generated low-level code so the single-core vendor compiler pipelines the loop. The factor / range is a hint for the desired initiation interval (II) — note it passes a range (1,64), i.e. a search bound for II, not a fixed value.
  • .vectorize() → maps chosen loop axes into SIMD form. Mechanically it adds another level of loop tiling by the given factors=[4,8,4] (one per axis), loads those slices into dedicated vector registers, and emits SIMD instructions.
📐 Where the 5 levels land: .to() covers ① task + ② tile (across cores); .pipeline() covers ③ loop; .vectorize() covers ④ data. Level ⑤ (VLIW/ILP) has no primitive — it's delegated to the vendor compiler, steered by the .pipeline II hint.

§5 — ARIES Representation & Optimizations

5.1 Representation Overview — the initial IR & ARIES's space-time encoding

Allo builds the initial IR; the GEMM (Fig 5) lowers to top_gemm (Fig 8) with the same loop structure, but the four loop bands are explicitly tagged with a space-time meaning:

Loop bandIndicesRole
8Ⓐi0,j0,k0L3 temporal mapping
8Ⓑi1,j1,k1L2 temporal mapping
8Ⓒi2,j2,k2L1 spatial mapping (inside adf.cell)
8Ⓓi3,j3,k3L1 temporal — per-core compute, extracted into func @gemm

Two ops carry the model:

  • adf.cell marks which loops are spatial. It supports up to one reduction loop + two non-reduction loops → a 3-D array that exploits IO reuse. (Their hardware constraint stated plainly: a 2-D PE array spatializes two axes, with one reduction axis.)
  • adf.dma is an n-dimensional data-slicing abstraction — moves between two memories with three slice pairs [offset],[size],[stride] (e.g. external %A → L1 %A_loc).
🔗 Contact with our spatial-dsl design (doc 02). ARIES also performs a space-time transform — but encodes it structurally (loop-band nesting depth + an adf.cell marker), not as an explicit affine (σ,π) map. And adf.cell's "1 reduction + 2 non-reduction loops" is exactly our rank constraint (2 spatial axes + reduction space R). Our design proposes the explicit-affine-map version of what ARIES expresses syntactically — more analyzable, less ad hoc.

5.3 Optimizations & Automation (Table 2: global, then local)

Global (graph-level, no hardware specifics):

  • broadcast-detection — walks all adf.dma, groups destinations sharing a source memory → load a tile once and broadcast (kills "load A0 repeatedly", Fig 10①).
  • data-forwarding — eliminates consecutive store/load pairs hitting the same external tile → forward PE→PE instead of round-tripping DRAM (Fig 10②).

Local (per hierarchy, ordered):

  • dma-to-io: adf.dma → adf.io.push/pop (memory↔IO-port).
  • adf-cell-create: extract the array into adf_cell0.
  • io-materialize: per .to()'s IO type, materialize ports as GMIO (AIE↔DRAM) or PLIO (AIE↔PL); for PLIO, synthesize the PL-side function.
  • io-packing: balance IO bandwidth — set port width / freq / burst length.
  • core-placement: map the 3-D logical array → 2-D physical array. To use shared memory + the cascade IO along the reduction dim, reduction-dim cores are placed adjacent, via three placers — horizontal / vertical / zigzag (Algorithm 1 = horizontal). User-overridable via .to().
  • io-placement: routing-aware — pick the interface-tile channel with least west/east congestion.
  • core vectorization (affine-unroll, affine-super-vectorize, aie-vectorize); PL lowering (axi-packing, burst-detection, pl-double-buffer, pipeline_ii default 1).
🔗 Two more validations of our design. (1) core-placement places reduction-dim cores adjacent specifically to use the cascade stream — exactly doc 02 §6's claim that spatial reductions lower to the AIE cascade. The three placers are heuristics for the cascade-chain layout (our open problem). (2) broadcast-detection + data-forwarding are the reuse/forwarding analyses we said our IR turns into geometry — ARIES does them operationally by matching adf.dma source/dest memories, not by affine region-overlap.
Headline insight & perf reason: ARIES argues top-down (abstract dataflow first, specialize later) beats bottom-up (optimizing one component forces edits across others); the unified IR keeps components mutually aware (change an IO width → buffer datatypes auto-update). Vs CHARM24: ARIES uses 352 AIEs (8% fewer) yet hits 1.31×/1.18× higher throughput — CHARM's PL-side double-buffer sync gives ~80% array efficiency, ARIES's full task-level pipeline gives ~95%.

§7 Conclusion & future work

ARIES = MLIR flow for AIE devices: a productivity-oriented programming model for multi-level parallelism + a unified IR for automated holistic optimization; open-source, end-to-end. Future work: integrate PL optimizations from ScaleHLS, HIDA, HeteroCL, HeteroFlow; and explore "more advanced DSE solutions to improve parallelism and data movement of multi-layer applications."

🔗 That last line is ARIES naming our spatial-dsl open problem #2 (the mapping/scheduling solver) as its own future work. The gap we identified is acknowledged by the authors themselves.

Our Takeaways (whole-paper)

  • The real contribution is the unified IR, not the programming model. The tile-based frontend is Triton-grid + Allo-scheduling resurfaced; the durable idea is one MLIR representation spanning AIE-core (AIEVec) / array (ADF) / PL (builtin), enabling top-down dataflow customization + cross-component-aware local opts.
  • Wins are about array efficiency, not compute. 1.17–1.59× over CHARM comes from 95% vs 80% array utilization (full task-level pipeline, cascade forwarding, avoiding L2 eviction) — keeping the array fed, not more FLOPs.
  • Space-time is present but implicit. ARIES encodes it as loop-band depth + adf.cell ("1 reduction + 2 non-reduction loops"); our spatial-dsl design proposes the explicit affine (σ,π) map for checkable legality. ARIES's core-placement (reduction-dim cores adjacent → cascade) validates our hardware grounding.
  • Scope is honestly dense affine. GEMM/TTM/TTMc/MTTKRP + ResNet convs — the same class our doc 03 scoped. No stencils; no data-dependent control.
  • ARIES flags our open problem as its own future work: advanced DSE for multi-layer parallelism + data movement — i.e. the mapping/scheduling solver.
